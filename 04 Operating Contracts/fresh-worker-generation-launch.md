# Recurring Worker Contract

This file owns only the scheduler/worker boundary. Cross-project safety, routing, repository, evidence, and coordination rules belong to the shared policy or the narrow live owner that actually enforces them.

## Invariants

1. **Exactly five canonical recurring workers per ChatGPT subscription partition stay enabled.** The swarm currently has two scheduler partitions, `S1` and `S2`, with five recurring workers each (10 total). Five remains the hard maximum inside each subscription partition; the existence of a second subscription does not authorize a sixth worker in either partition. Never pause, disable, delete, retire, reschedule, rename, or replace a canonical worker unless the user explicitly instructs that exact scheduler mutation. An unexpected disabled canonical worker is degradation to repair, not a safe steady state.
2. **The scheduler provides recurrence only.** Enabled state, schedules, timestamps, claims, leases, heartbeats, and reports do not prove that work is happening.
3. **Every recurring worker is a bounded sibling-recovery participant.** A worker must never administer itself. After its own fresh RUNNING report exists and `worker_report_history.py begin` succeeds, it runs `python C:\Users\Lauri\Desktop\vault\tools\stack_atlas.py fleet-watch --worker-id <own-automation-id>` once; that local-only command resolves the worker's subscription partition and reads only that partition's five canonical current reports and machine start receipts for actionable sibling recovery. Bootstrap may read the global 5+5 view for observability, but recurring-worker recovery never crosses subscription partitions. Archive metrics and MCP/runtime evidence may corroborate, but scheduler listing is not the discovery path. Only entries in `recovery_candidates` are actionable. A fresh `RUNNING` report may briefly precede its machine start receipt; `START_RECEIPT_PENDING` is tolerated for the bounded two-minute registration grace and authorizes no scheduler action. `RUNNING_WITHOUT_START_RECEIPT` after that grace is degraded local startup evidence and may become an actionable sibling recovery candidate. A `RECOVERY_PENDING` suspect means another canonical worker already recorded a successful targeted recovery that has not yet been disproved by newer local start evidence, so perform no scheduler action for that sibling. For each actionable exact canonical sibling in the same subscription partition, issue at most one targeted idempotent `is_enabled=true` write, preserving prompt/title/schedule/timezone/stagger. Never attempt to administer a sibling belonging to the other ChatGPT subscription. After a successful write, immediately record `Peer recovery: sibling=<automation-id> action=is_enabled=true result=success at=<ISO-8601>` in the acting worker's own durable findings before product mutation continues; a failed write must record `result=failed` and does not suppress a later sibling retry. Do not preflight with a broad scheduler read, poll, loop, touch retired/test/non-fleet tasks, or create a replacement. When fleet-watch marks a suspect RECOVERY_PENDING, perform no scheduler write; if that sibling still has no fresh start after its next locally observed hourly start phase plus the bounded grace, fleet-watch may promote it to RECOVERY_RETRY_NEEDED and authorize one new targeted re-enable. A newer sibling start consumes an older recovery immediately; if that newer run then remains RUNNING without its required machine start receipt beyond the registration grace, treat it as a fresh startup failure rather than extending the old recovery cooldown. This distributed recovery remains available when the supervising/manual chat is absent or fails. Older launcher wording that asks for a full scheduler/report pre-startup-failure signature is satisfied by this local missed-cadence/start-evidence rule; do not add a scheduler-list/read preflight.
4. **Use current direction and live state.** A worker follows its current run prompt and the live target repo/runtime. Read the applicable repo `AGENTS.md` immediately before the first mutation. Do not make Atlas, Vault, reports, history, or scheduler metadata a generic startup gate.
5. **Do product work for the useful run window.** Prefer concrete player-visible implementation and acceptance. About 24 minutes remains the timed utilization target and is not a reason to idle or pad. Finishing one bounded slice early should lead to another safe useful action while meaningful time remains. Utilization never requires creating a new work identity; work identity follows the canonical shared issue-first rules, so continue existing WIP/current acceptance identity instead of inventing filler. Timed finalization keeps the existing >=80% completion guard, with only user interruption/supersession or the documented true no-safe-work exception allowed to finish earlier.
6. **A blocker changes scope; it does not end unrelated work.** Pending CI, an occupied Unreal/build lane, resource pressure, a route failure, or another actor owning an exact mutation scope blocks only that dependency. Preserve its gate and continue safe non-conflicting work when available. If a required tool or binding is missing, unavailable, stale, disconnected, or unexpectedly rejected, refresh/re-discover the available tool bindings and retry the smallest supported call before using a supported fallback. Treat missing tool exposure as route state, not proof that the capability is absent. **Transient startup/compliance-evidence failure is run-local degradation, never run cancellation or scheduler authority. One failed bootstrap, shared-rule read, report-helper call, binding lookup, or other tool call must not end the timed run.** Refresh/re-discover and retry through an approved route; if that exact path remains unavailable, continue safe in-scope product work through another approved route or another ready non-conflicting contribution. Only after bounded evidence shows that no approved route and no safe in-scope contribution can advance may the current run yield under the documented true no-safe-work exception, and even then the worker remains enabled for its next scheduled run. Failure to create or validate a timed report/start receipt means compliance evidence is missing for that run; it never authorizes declaring the worker permanently broken, suppressing future scheduled runs, or pausing, disabling, rescheduling, renaming, replacing, or otherwise administering itself. **A recurring worker must never issue any scheduler mutation against its own automation id.** Sibling administration is limited to the bounded is_enabled=true recovery in invariant 3.
7. **BusyCoordinator is collision control only.** Claim only the exact shared mutation scope when collision risk exists. It is not backlog, scheduling, liveness, priority, capacity, or worker supervision.
8. **Keep reporting durable and population-separated.** Immediately before writing or finalizing a worker report, after a machine route is established, read this contract once; do not rely on copied or remembered reporting instructions. Reporting is evidence/observability only and never completion, scheduling, supervision, admission, a queue, behavior authority, or policy authority; repeated report findings never promote themselves into rules. Both timed and manual/on-demand workers record the same structured finding fields: `finding_tags` and `findings`. Canonical tags are `bug`, `error`, `regression`, `wrapper_anomaly`, `route_problem`, `contention`, `performance`, `improvement`, `tooling`, `ci`, `build`, `proof`, `resource`, and `other`; use `finding_tags: none` and `findings: none` when nothing material was observed.

   **Timed recurring runs** keep the existing `worker-reports/current/<automation-id>.md` -> `worker-reports/history` lifecycle and `worker-reports/metrics.json`. Use the canonical keys `automation_id`, optional `display_label`, `started_at`, `last_activity_at`, `repo`, `scope`, `state`, `outcome`, `mutation`, `validation`, `remaining_gate`, `finding_tags`, and `findings`; when a run publishes a durable proof/capture bundle, use optional `proof_artifact` for its canonical review/index/receipt path and `proof_artifact_sha256` for that exact file digest. Historical `proof_index` / `proof_index_sha256` remain accepted aliases. These fields are navigation/integrity evidence only and never imply visual review or PASS. Near the start of every timed run, after the first bounded scope selection and before any command that may consume a material part of the useful run window, create or refresh that current report with `state: RUNNING` and `started_at` set to the current machine time, then immediately register the start with `python C:\Users\Lauri\Desktop\vault\tools\worker_report_history.py begin --report <path>`. The begin command writes the machine-observed start receipt used for timed duration/utilization; self-reported backdating does not count. For migration compatibility with the known static-launcher legacy preamble only, `begin` may canonicalize that exact RUNNING startup shape by filling honest startup placeholders and converting empty-list finding fields to `none`; arbitrary incomplete reports still fail closed, and the next natural report update must replace startup placeholders with the real repo/scope/outcome evidence. Update the current report at natural checkpoints when scope/evidence/findings materially change. Finalize and archive it with `python C:\Users\Lauri\Desktop\vault\tools\worker_report_history.py archive --report <path>`. A current timed `RUN_FINISHED` without matching machine start evidence is rejected; successful archive consumes the receipt. If the archiver rejects premature timed `RUN_FINISHED`, the run is not finished: keep the current report `RUNNING`, continue useful work inside existing WIP/current work identity, and retry finalization only when valid. Duration and target utilization remain derived observability metadata, while the timed finalization guard enforces >=80% utilization except user interruption/supersession or the documented true no-safe-work condition. The guard is not scheduling, priority, product acceptance, or permission to manufacture filler issues/PRs.

   **Manual/on-demand execution runs are mandatory and minimal; ordinary conversation is not a run.** Each substantive user-driven execution run must create its fresh filesystem-safe identity/current file through `python C:\\Users\\Lauri\\Desktop\\vault\\tools\\worker_report_history.py create-manual --repo <repo> [--stem <short-purpose>] [--scope <scope>] [--run-mode continuation]`. The helper generates a collision-resistant `run_id` and atomically creates exactly one `worker-reports/manual/current/<run-id>.md` without overwriting an existing report. Do not handcraft manual run IDs or current report paths. Normal answers, clarifications, acknowledgements, and correction-only handling do not open a manual worker report. The required fields are only `run_id`, `started_at`, `last_activity_at`, `repo`, `state`, and a short `outcome`; `display_label`, `scope`, `finding_tags`, `findings`, `stop_reason`, and proof-artifact fields are optional. For `go`/`continue` on an established scope, add optional `run_mode: continuation`; bounded one-shot execution tasks may omit it. If a continuation is interrupted/superseded by a correction, close that run with `stop_reason: user_interrupted` when applicable and handle the correction outside the worker-run population. Open the report once immediately before the first execution tool call and close/archive it once immediately after the last execution tool call before returning control to the user. Do not checkpoint routine progress and do not copy commands, process IDs, Busy claims, GitHub/PR chronology, CI output, validation logs, or other telemetry already preserved by their owning systems. Use optional `findings` only for a material error, blocker, workflow defect, or reusable blindspot worth aggregating. Manual history derives start/finish/duration and aggregate finding statistics, never timed utilization/fleet statistics. A manual report is accounting/feedback evidence, not liveness, supervision, admission, or a queue.

   **Manual reporting sanity is observational, not a target.** `04 Operating Contracts/manual-worker-sanity-baseline.json` fixes `2026-09-06T21:26:41+03:00` (PR #658) as the zero-point baseline. The general manual score measures reporting friction plus lifecycle mistakes across actual execution runs; it does **not** use mixed task duration. Continuation (`go`/`continue`) duration and fragmentation are a separate projection with their own sample count and baseline, so bounded one-shot tasks and correction handling cannot make a `go` run look short. Neither score controls scheduling, completion, worker evaluation, admission, product acceptance, or run length, and no worker may pad work to improve it.


9. **Repair minimally.** Distributed workers and supervising/manual chat use the same local-evidence-first recovery rule: identify the exact suspect canonical slot from reports/start receipts, then perform only the targeted idempotent is_enabled=true recovery for that existing sibling/slot. Never create verifier, spare, overlap, replacement, or temporary sixth workers inside a subscription partition, and never create an eleventh recurring worker globally while the topology is 5+5.
