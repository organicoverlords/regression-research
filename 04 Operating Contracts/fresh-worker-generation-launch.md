# Fresh Worker Generation Launch Contract

Use this contract whenever starting a new recurring worker generation or replacing workers that are stale, buggy, or missing required tools.

## Hard capacity: five workers total

- **Five is a hard maximum for the recurring worker fleet.** Never have more than five enabled recurring repo workers, even temporarily during replacement, recovery, verification, or generation turnover.
- **Replacement is one-for-one at the cap.** When five workers are enabled, retire/disable a proven-bad slot before creating or enabling its replacement. A verifier, spare, overlap worker, or "temporary sixth" is not allowed.
- Preserve healthy workers and fill only missing or proven-bad slots until the active enabled fleet reaches five. "Arm five" means reconcile the fleet to **at most five total enabled workers**, not add five workers on top of an existing fleet.
- A full healthy fleet is five workers. Fewer than five is allowed while a slot is intentionally missing or being repaired; more than five is never allowed.

## Mode decision: status first; replace only proven-bad slots

- Perform **one bounded status read** of the intended five worker slots before scheduler mutation: enabled state, schedule, and latest available run/report evidence. Do not repeatedly re-read the scheduler during setup.
- A worker whose own latest run/report clearly proves a required-tool failure (`RESET_REQUIRED: TOOLS`, `LOCAL_TOOL_NOT_EXPOSED`, or equivalent evidence-backed failure) is a bad slot: retire/remove that worker from the active set and create a fresh replacement for that slot. Start with Worker 1 when Worker 1 is bad.
- Preserve healthy intended workers. Re-enable an otherwise healthy paused/disabled worker when needed; do not recreate healthy slots merely to make the fleet uniform.
- Replace the **whole generation** only when the user explicitly requests all-fresh workers, describes the whole fleet as poisoned/contaminated, or current evidence shows a shared generation defect. One bad worker is not evidence that all five are bad.
- Historical reports, templates, schedules, and memory are evidence only. Current user direction and current run/report evidence control the decision.
- Reconciling the five intended slots is one setup pass. Do not insert proof ceremonies between Workers 1-5; establish five enabled slots, then use Worker 1 execution proof as the first acceptance gate.

1. **Check once, replace minimally.** Read current worker status once. Retire/recreate only slots with current evidence of poisoning, stale/broken execution, or required-tool failure; preserve healthy slots and their schedules where practical. Do not inherit a failed worker's conversation state as launch authority.
2. **Arm the intended five in one setup pass and schedule Worker 1 once with enough runway.** Use about **5 minutes** as the normal Worker 1 target. If setup latency makes that too short, choose a later safe launch time **once** before the setup report. The launch window is a scheduling parameter, not a precision invariant: a longer runway is preferable to repeatedly moving Worker 1 forward. Workers 2-5 may remain on healthy existing schedules or be staggered behind Worker 1 as needed; all five intended slots must be enabled before setup is reported complete.
3. **Verify once, then lock the scheduler phase.** After the necessary mutations, perform one bounded readback confirming the intended five enabled slots and that Worker 1 has a future launch with reasonable runway. If the committed Worker 1 time is already invalid (past/current minute or too close to finish setup safely), move it forward **once** before reporting. Do not move Worker 1 merely because time elapsed while inspecting or reporting. Give one compact setup report and end the arm phase.
4. **Go work; do not idle or re-arm.** Immediately return to substantive repository work in the same chat. From the setup report until the first post-launch check, do not rearm, reschedule, replace, pause, disable, or otherwise mutate worker scheduling. Waiting, rapid polling, scheduler normalization, repeated verification, or keeping the turn alive only to watch a timer is not productive supervision.
5. **Bind the required local tool route, but treat transient surface loss as normal.** Put the required tool tag at the start of each worker prompt (currently `@plugin2`). GitHub mutation still goes through the user's local machine using local `git`/`gh` via that route. The tool surface is known to be flaky: refresh/re-discovery/reload is **repeatable, explicitly allowed, and may be mandatory many times** when bindings disappear or go stale. Do not impose a one-refresh ceiling or a fixed failure-count cutoff. Preserve the active task and any returned process IDs across refreshes; at natural work boundaries, refresh/re-discover as needed, retry the same process/operation when appropriate, and continue safe useful work through other actually exposed capabilities between recovery attempts. Never tight-loop refreshes or use authentication as recovery. Declare a route unavailable only from current repeated evidence that it remains unusable after appropriate recovery, never from a missing namespace, one/few failures, or an arbitrary retry count. Never claim `RESET_REQUIRED: TOOLS` or equivalent from assumption; route-failure claims require real returned failure evidence.
6. **Generic mission, live queue.** Workers orient from current repo authority and live standalone BusyCoordinator state, then work current PRs/issues. They are executors/orchestrators, not status monitors. If the live issue/PR queue is genuinely exhausted, read the project North Star, identify a concrete unmet outcome, avoid duplicates, create at most one bounded real tracker item when warranted, and start advancing it in the same run.
7. **A scheduled/enabled worker is NOT a proven worker.** Fresh-generation acceptance requires observed live proof from Worker 1's first launch: the timer actually fired; the required local process tool actually executed; local repo and local GitHub CLI checks succeeded; repo/head/remote identity was captured; current ownership was checked; and the worker selected and began a real bounded work scope. A task card, enabled flag, timestamp, or `last_run_time` alone is insufficient.
8. **Use an explicit first-launch proof surface.** Worker 1 may write a local non-Git proof record only after the required tool plus local `git`/`gh` succeed, ownership is checked, and substantive work begins. Never write the proof optimistically before those facts are true.
9. **Verify Worker 1 while doing real work, not by idling.** Continue substantive repo work until Worker 1's launch window has elapsed, then check the automation run and proof surface at a natural work boundary. If Worker 1 is healthy, continue the supervising chat's repo work until the current bounded task is done or a genuine task-level blocker is reached.
10. **A failed first launch replaces only the failed slot.** Do not call Worker 1 failed before its committed `DTSTART` plus normal scheduler latency has elapsed. If it then does not fire, cannot use the required tool, reports an evidence-backed tool/startup failure, fails live orientation, or lacks substantive launch proof, retire/recreate **Worker 1 only**, schedule the replacement once with enough runway (normally about 5 minutes; longer if setup requires it), perform one bounded readback, report the repair compactly, return to substantive repo work, and check again after launch. Preserve Workers 2-5 unless their own current run/report evidence proves they are bad or there is evidence of a shared generation defect.
11. **The current chat is the supervisor; do not create a verifier timer as a substitute.** With all five worker slots armed, the supervising chat owns launch acceptance. A separate wakeup/verifier automation consumes capacity and recreates the same offloading failure. The supervisor reports setup, works productively, verifies Worker 1, repairs if needed, and keeps working.
12. **Keep user-visible supervision bounded and informative.** Report material setup, repair, and acceptance transitions. During longer repo work, give concise progress only after meaningful work or a direction change. Never use silence plus a continuously running tool timer as the supervision mechanism.
13. **Worker execution may never administer the scheduler.** A scheduled worker must not call automation-management tools, disable/pause/rename/reschedule itself, or mutate siblings. Tool loss is local to that route, not a scheduler event. A worker that previously proved the local route in an earlier run is not replaced merely because a later run has one or two route failures. Even after the bounded recovery sequence is exhausted, continue other safe useful non-mutating work when possible and leave the recurring schedule enabled. Fleet repair belongs exclusively to the supervising chat.

This launch contract is an orchestration invariant. **Five enabled recurring workers is the hard fleet cap. Check status once, preserve healthy slots, replace only proven-bad slots one-for-one, reconcile to no more than five enabled workers, schedule Worker 1 once with enough runway, report setup, go work, then perform one post-launch acceptance check.** Never create a sixth worker as a verifier, spare, overlap, or temporary replacement. Do not trade fleet liveness for scheduler precision, and do not re-enter the arm phase merely because time elapsed. Schedule configuration is setup; observed execution proof is acceptance.
