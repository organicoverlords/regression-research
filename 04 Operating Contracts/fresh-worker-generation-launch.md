# Recurring Worker Contract

This file owns only the scheduler/worker boundary. Cross-project safety, routing, repository, evidence, and coordination rules belong to the shared policy or the narrow live owner that actually enforces them.

## Invariants

1. **Five is a hard maximum for the recurring worker fleet.** Never enable more than five recurring repo workers.
2. **The scheduler provides recurrence only.** Enabled state, schedules, timestamps, claims, leases, heartbeats, and reports do not prove that work is happening.
3. **Workers never administer workers.** A scheduled worker must not pause, disable, enable, reschedule, rename, replace, create, or delete itself or a sibling. Fleet administration belongs to the supervising chat.
4. **Use current direction and live state.** A worker follows its current run prompt and the live target repo/runtime. Read the applicable repo `AGENTS.md` immediately before the first mutation. Do not make Atlas, Vault, reports, history, or scheduler metadata a generic startup gate.
5. **Do product work for the useful run window.** Prefer concrete player-visible implementation and acceptance. About 24 minutes is a utilization target, not a reason to idle or pad. Finishing one bounded slice early should lead to another safe useful slice while meaningful time remains.
6. **A blocker changes scope; it does not end unrelated work.** Pending CI, an occupied Unreal/build lane, resource pressure, a route failure, or another actor owning an exact mutation scope blocks only that dependency. Preserve its gate and continue safe non-conflicting work when available.
7. **BusyCoordinator is collision control only.** Claim only the exact shared mutation scope when collision risk exists. It is not backlog, scheduling, liveness, priority, capacity, or worker supervision.
8. **Keep reporting durable and population-separated.** Immediately before writing or finalizing a worker report, after a machine route is established, read this contract once; do not rely on copied or remembered reporting instructions. Reporting is evidence/observability only and never completion, scheduling, supervision, admission, or a queue. Both timed and manual/on-demand workers record the same structured finding fields: `finding_tags` and `findings`. Canonical tags are `bug`, `error`, `regression`, `wrapper_anomaly`, `route_problem`, `contention`, `performance`, `improvement`, `tooling`, `ci`, `build`, `proof`, `resource`, and `other`; use `finding_tags: none` and `findings: none` when nothing material was observed.

   **Timed recurring runs** keep the existing `worker-reports/current/<automation-id>.md` -> `worker-reports/history` lifecycle and `worker-reports/metrics.json`. Use the canonical keys `automation_id`, optional `display_label`, `started_at`, `last_activity_at`, `repo`, `scope`, `state`, `outcome`, `mutation`, `validation`, `remaining_gate`, `finding_tags`, and `findings`; add landed/published proof fields when applicable. Near the start of every timed run, after the first bounded scope selection and before any command that may consume a material part of the useful run window, create or refresh that current report with `state: RUNNING` and the actual `started_at`; update it at natural checkpoints when scope/evidence/findings materially change. Finalize and archive it with `python C:\Users\Lauri\Desktop\vault\tools\worker_report_history.py archive --report <path>`. Timed history/metrics continue to derive elapsed duration, the 24-minute target, and utilization. If the archiver rejects a premature timed `RUN_FINISHED`, the run is not finished: keep the current report `RUNNING`, continue useful work, and retry finalization only when valid.

   **Manual/on-demand runs** are separate. Each substantive user-driven worker execution turn gets a fresh filesystem-safe `run_id` and writes `worker-reports/manual/current/<run-id>.md` with `run_id`, optional `display_label`, `started_at`, `last_activity_at`, `repo`, `scope`, `state`, `outcome`, `mutation`, `validation`, `remaining_gate`, `finding_tags`, and `findings`; add proof fields when applicable. Create it near run start, update it at natural material checkpoints, and archive finalized reports with the same command. The default archive path is `worker-reports/manual/history` and metrics are `worker-reports/manual/metrics.json`. Manual reports still derive start/finish/elapsed duration and aggregate finding tags, but they never receive or contribute to the timed 24-minute target/utilization/fleet statistics. Timed consumers must ignore manual records and manual consumers must ignore timed records. A report is evidence of that run, not proof of present liveness.

9. **Repair minimally.** The supervisor replaces only a currently proven-bad slot and never exceeds the five-worker cap. Do not create verifier, spare, overlap, or temporary sixth workers.
