# Fresh Worker Generation Launch Contract

Use this contract whenever starting a new recurring worker generation or replacing workers that are stale, buggy, or missing required tools.

## Hard fleet cap: five means maximum

- The recurring repository-worker fleet has a **hard cap of five enabled worker slots total**. Five is the maximum, not a minimum or soft target.
- Arming, replacement, recovery, verification, and fresh-generation setup must never create or keep a sixth active recurring worker. A separate verifier/wakeup worker also counts against the cap and therefore must not be added when five worker slots are already armed.
- Preserve healthy workers and fill or replace only within the five-slot cap. Replace one bad slot with one fresh slot; do not temporarily exceed five during replacement.
- The fleet-size cap is independent of tool recovery: refresh/re-discovery/reload may happen repeatedly as needed without creating additional recurring workers.

## Mode decision: bugged means fresh replacement

- `FRESH_GENERATION` is mandatory when the current user says the workers/fleet are bugged, poisoned, stale, contaminated, missing required tools, or otherwise need fresh sessions, or when current live evidence shows that condition. That statement/evidence is already sufficient justification for replacement. Do **not** re-enable an old worker, demand an extra proof ceremony, or reinterpret a request to arm the workers as `REARM_EXISTING`.
- `REARM_EXISTING` is only valid when current evidence says the intended workers are healthy and merely paused/disabled, and there is no current contamination/bug report requiring fresh sessions.
- Historical reports, templates, schedules, and memory are evidence only. If they conflict with this contract or current user/live state, they cannot change the mode decision.
- Arming all five fresh workers is one setup pass. Do not apply a one-mutation-per-proof rule between Workers 1-5; create and enable the full generation first, then use Worker 1 execution proof as the acceptance gate.

1. **Replace poisoned workers; do not merely re-arm them.** Retire stale/buggy/missing-tool workers and create a fresh generation. Do not inherit their conversation state as launch authority.
2. **Arm the full five-worker generation in one setup pass.** The normal generation is five generic orchestrator/execution workers. Create and enable all five before calling setup complete. Worker 1 must be scheduled to launch immediately/as soon as the scheduler permits. Workers 2-5 may be staggered behind Worker 1 to reduce collision, but all five must already be armed.
3. **Report the arm immediately.** As soon as all five workers are armed and Worker 1 has an immediate launch scheduled, give the user one compact setup report. Do not leave the user staring at an expanding tool-call timer with no explanation. The report may say the fleet is armed, but must not call Worker 1 healthy or proven yet.
4. **Do not hang around waiting for Worker 1.** After the arm report, immediately return to substantive repository work in the same chat. Use the live portfolio/repo/coordinator state and advance the highest-value safe unowned work. Waiting, rapid polling, or keeping the turn alive only to watch a timer is not productive supervision.
5. **Bind and actually invoke the required local tool route.** Put the required tool tag at the start of each worker prompt (currently `@plugin2`). GitHub work goes through the user's local machine using local `git`/`gh` via that process route. Never claim `RESET_REQUIRED: TOOLS` or equivalent from assumption: the worker must actually attempt the required tool first and base any route-failure claim on the returned failure.
6. **Generic mission, live queue.** Workers orient from current repo authority and live standalone BusyCoordinator state, then work current PRs/issues. They are executors/orchestrators, not status monitors. If the live issue/PR queue is genuinely exhausted, read the project North Star, identify a concrete unmet outcome, avoid duplicates, create at most one bounded real tracker item when warranted, and start advancing it in the same run.
7. **A scheduled/enabled worker is NOT a proven worker.** Fresh-generation acceptance requires observed live proof from Worker 1's first launch: the timer actually fired; the required local process tool actually executed; local repo and local GitHub CLI checks succeeded; repo/head/remote identity was captured; current ownership was checked; and the worker selected and began a real bounded work scope. A task card, enabled flag, timestamp, or `last_run_time` alone is insufficient.
8. **Use an explicit first-launch proof surface.** Worker 1 may write a local non-Git proof record only after the required tool plus local `git`/`gh` succeed, ownership is checked, and substantive work begins. Never write the proof optimistically before those facts are true.
9. **Verify Worker 1 while doing real work, not by idling.** Continue substantive repo work until Worker 1's launch window has elapsed, then check the automation run and proof surface at a natural work boundary. If Worker 1 is healthy, continue the supervising chat's repo work until the current bounded task is done or a genuine task-level blocker is reached.
10. **A failed first launch starts an immediate repair loop.** If Worker 1 does not fire, cannot use the required tool, emits an unsupported reset/error, fails live orientation, or lacks substantive launch proof, retire/recreate that failed Worker 1, schedule the replacement immediately, report the repair compactly, return to substantive repo work, and verify again after its launch window. Repeat this work-and-verify cycle until Worker 1 is proven healthy. Preserve Workers 2-5 unless evidence shows the whole generation shares the defect.
11. **The current chat is the supervisor; do not create a verifier timer as a substitute.** With all five worker slots armed, the supervising chat owns launch acceptance. A separate wakeup/verifier automation consumes capacity and recreates the same offloading failure. The supervisor reports setup, works productively, verifies Worker 1, repairs if needed, and keeps working.
12. **Keep user-visible supervision bounded and informative.** Report material setup, repair, and acceptance transitions. During longer repo work, give concise progress only after meaningful work or a direction change. Never use silence plus a continuously running tool timer as the supervision mechanism.

This launch contract is an orchestration invariant. **Arm all five, report setup, work, verify Worker 1, repair-and-repeat if needed, then keep working.** Schedule configuration is setup; observed execution proof is acceptance.
