# Recurring Worker Contract

This file owns only the scheduler/worker boundary. Cross-project safety, routing, repository, evidence, and coordination rules belong to the shared policy or the narrow live owner that actually enforces them.

## Invariants

1. **Each recurring subscription partition has a hard maximum of five workers.** `S1` and `S2` are both canonical recurring partitions with five known worker identities each, so the two known partitions permit up to ten recurring workers total. Never create or enable a sixth worker inside either partition. Never mutate a canonical worker merely to make Atlas/topology/history internally consistent. Fleet-watch/local report evidence alone is never scheduler-write authority: before any enable/rearm/disable action, the supervising chat must probe that exact automation in the ChatGPT scheduler and reconcile `is_enabled` plus `last_run_time`; a current live scheduler run overrides stale local report evidence.
2. **The scheduler provides recurrence only.** Enabled state, schedules, timestamps, claims, leases, heartbeats, and reports do not prove that work is happening.
3. **Recurring workers observe fleet health but never administer scheduler state.** A recurring worker must never administer itself or any sibling. After its own fresh RUNNING report exists and `worker_report_history.py begin` succeeds, it may run `python C:\Users\Lauri\Desktop\vault\tools\stack_atlas.py fleet-watch --worker-id <own-automation-id>` once to obtain bounded canonical-fleet recovery evidence. `recovery_candidates`, `RECOVERY_PENDING`, and related states are handoff evidence only for a recurring worker and authorize no scheduler write by that worker. Exact targeted `is_enabled=true` recovery, when `worker_recovery_guard.py` authorizes it, belongs to the supervising/manual ChatGPT session or explicit operator handoff and must preserve prompt/title/schedule/timezone/stagger. Do not preflight with a broad scheduler read, poll, loop, touch retired/test/non-fleet tasks, or create a replacement.
4. **Use current direction and live state; unified `find` is the first discovery surface.** A worker follows its current run prompt plus fresh bootstrap/live target repo/runtime evidence. Reuse already-held task context first. When the exact owner, matching WIP, issue/PR, branch/commit, runtime trace, worker report, artifact, or historical thread is unknown, run one `python C:\Users\Lauri\Desktop\vault\tools\stack_atlas.py find <natural-language-query>` pass instead of separately searching GitHub, Git, Vault, reports, or logs. The query searches the materialized local Git/branch history, GitHub issue/PR/body/comments through the existing cache/materializer, MCP process receipts plus transport/watchdog evidence, runner/CI/machine/coordinator observations, worker reports, artifacts, memories/timeline, Atlas navigation, and live-swarm hints. Search clusters are correlation only: each member keeps its own authority/verdict, and worker reports never substitute for runtime receipts/logs when asking what actually executed. Repository grepping/recursive scans are forbidden as discovery fallback; once an exact implementation owner/path is known, targeted source/caller tracing is normal engineering work. Use `memory_bank.py context <query>` and then at most one `timeline <query>` only as drill-down after `find` surfaces a relevant historical thread or when a concrete historical fact remains materially unknown. For stack/MCP/infra mutation, bootstrap supplies current topology/recovery orientation; use full Atlas inventory only if bootstrap plus targeted `find` still cannot bound the dependency/blast radius. Historical search evidence is never current truth.
5. **Do product work for the useful run window.** Prefer concrete player-visible implementation and acceptance. About 24 minutes remains the timed utilization target and is not a reason to idle or pad. Finishing one bounded slice early should lead to another safe useful action while meaningful time remains. Utilization never requires creating a new work identity; work identity follows the canonical shared issue-first rules, so continue existing WIP/current acceptance identity instead of inventing filler. Timed finalization keeps the existing >=80% completion guard, with only user interruption/supersession or the documented true no-safe-work exception allowed to finish earlier.
6. **A blocker changes route; it does not end unrelated work.** Pending CI, an occupied Unreal/build lane, resource pressure, a route failure, or another actor owning an exact mutation scope blocks only that dependency. Preserve its gate and continue safe non-conflicting work when available. Scope, repository, project, issue, branch, or worktree boundaries constrain relevance and collision safety; exhausting one is never itself a yield condition. If a required tool or binding is missing, unavailable, stale, disconnected, or unexpectedly rejected, refresh/re-discover the available tool bindings and retry the smallest supported call before using a supported fallback. Treat missing tool exposure as route state, not proof that the capability is absent. **Transient startup/compliance-evidence failure is run-local degradation, never run cancellation or scheduler authority. One failed bootstrap, shared-rule read, report-helper call, binding lookup, or other tool call must not end the timed run.** Refresh/re-discover and retry through an approved route; if that exact path remains unavailable, continue safe relevant product work through another approved route or another ready non-conflicting contribution. The documented true no-safe-work exception applies only when bounded evidence establishes that an actual platform/tool/safety/authorization/unrecoverable external limit prevents any further useful progress toward the current objective; pending CI, an occupied lane, or lack of ready work inside an inferred scope does not qualify. Even then the worker remains enabled for its next scheduled run. Failure to create or validate a timed report/start receipt means compliance evidence is missing for that run; it never authorizes declaring the worker permanently broken, suppressing future scheduled runs, or pausing, disabling, rescheduling, renaming, replacing, or otherwise administering itself. **A recurring worker must never issue any scheduler mutation against its own automation id or any sibling automation id.**
7. **BusyCoordinator is collision control only.** Claim only the exact shared mutation scope when collision risk exists. It is not backlog, scheduling, liveness, priority, capacity, or worker supervision. Before starting a new output for an objective whose surrounding work is materially unknown, use unified `find` to see the existing implementation/proof/integration evidence and choose a genuinely missing contribution; parallel workers should complement the same objective with disjoint useful evidence/results rather than independently re-solving the same acceptance.
8. **Keep reporting durable and population-separated.** Immediately before writing or finalizing a worker report, after a machine route is established, read this contract once; do not rely on copied or remembered reporting instructions. Reporting is evidence/observability only and never completion, scheduling, supervision, admission, a queue, behavior authority, or policy authority; repeated report findings never promote themselves into rules. Both timed and manual/on-demand workers record the same structured finding fields: `finding_tags` and `findings`. Canonical tags are `bug`, `error`, `regression`, `wrapper_anomaly`, `route_problem`, `contention`, `performance`, `improvement`, `tooling`, `ci`, `build`, `proof`, `resource`, and `other`; use `finding_tags: none` and `findings: none` when nothing material was observed.

   **Timed recurring runs** keep the existing `worker-reports/current/<automation-id>.md` -> `worker-reports/history` lifecycle and `worker-reports/metrics.json`. Use the canonical keys `automation_id`, optional `display_label`, `started_at`, `last_activity_at`, `repo`, `scope`, `state`, `outcome`, `mutation`, `validation`, `remaining_gate`, `finding_tags`, and `findings`; when a run publishes a durable proof/capture bundle, use optional `proof_artifact` for its canonical review/index/receipt path and `proof_artifact_sha256` for that exact file digest. Historical `proof_index` / `proof_index_sha256` remain accepted aliases. These fields are navigation/integrity evidence only and never imply visual review or PASS. Near the start of every timed run, after the first bounded scope selection and before any command that may consume a material part of the useful run window, create or refresh that current report with `state: RUNNING` and `started_at` set to the current machine time, then immediately register the start with `python C:\Users\Lauri\Desktop\vault\tools\worker_report_history.py begin --report <path>`. The begin command writes the machine-observed start receipt used for timed duration/utilization; self-reported backdating does not count. For migration compatibility with the known static-launcher legacy preamble only, `begin` may canonicalize that exact RUNNING startup shape by filling honest startup placeholders and converting empty-list finding fields to `none`; arbitrary incomplete reports still fail closed, and the next natural report update must replace startup placeholders with the real repo/scope/outcome evidence. Update the current report at natural checkpoints when scope/evidence/findings materially change. Finalize and archive it with `python C:\Users\Lauri\Desktop\vault\tools\worker_report_history.py archive --report <path>`. A current timed `RUN_FINISHED` without matching machine start evidence is rejected; successful archive consumes the receipt. If the archiver rejects premature timed `RUN_FINISHED`, the run is not finished: keep the current report `RUNNING`, continue useful work inside existing WIP/current work identity, and retry finalization only when valid. Duration and target utilization remain derived observability metadata, while the timed finalization guard enforces >=80% utilization except user interruption/supersession or the documented true no-safe-work condition. The guard is not scheduling, priority, product acceptance, or permission to manufacture filler issues/PRs.

   **Manual/on-demand execution runs are mandatory and minimal; ordinary conversation is not a run.** Each substantive user-driven execution run must create its fresh filesystem-safe identity/current file through `python C:\\Users\\Lauri\\Desktop\\vault\\tools\\worker_report_history.py create-manual --repo <repo> [--stem <short-purpose>] [--scope <scope>] [--run-mode continuation]`. The helper generates a collision-resistant `run_id` and atomically creates exactly one `worker-reports/manual/current/<run-id>.md` without overwriting an existing report. Do not handcraft manual run IDs or current report paths. Normal answers, clarifications, acknowledgements, and correction-only handling do not open a manual worker report. The required fields are only `run_id`, `started_at`, `last_activity_at`, `repo`, `state`, and a short `outcome`; `display_label`, `scope`, `finding_tags`, `findings`, `stop_reason`, and proof-artifact fields are optional. For `go`/`continue` on an established scope, add optional `run_mode: continuation`; bounded one-shot execution tasks may omit it. If a continuation is interrupted/superseded by a correction, close that run with `stop_reason: user_interrupted` when applicable and handle the correction outside the worker-run population. Open the report once immediately before the first execution tool call and close/archive it once immediately after the last execution tool call before returning control to the user. Do not checkpoint routine progress and do not copy commands, process IDs, Busy claims, GitHub/PR chronology, CI output, validation logs, or other telemetry already preserved by their owning systems. Use optional `findings` only for a material error, blocker, workflow defect, or reusable blindspot worth aggregating. Manual history derives start/finish/duration and aggregate finding statistics, never timed utilization/fleet statistics. A manual report is accounting/feedback evidence, not liveness, supervision, admission, or a queue.

   **Manual report metrics are auxiliary diagnostics, not system truth.** `04 Operating Contracts/manual-worker-sanity-baseline.json` preserves the historical revision-3 report-derived trend from the fixed `2026-09-06T21:26:41+03:00` (PR #658) zero point, but that legacy delta is not eligible as the current sanity headline. Worker report fields, wording, length, lifecycle narration, self-asserted success, and report-derived duration/fragmentation may annotate or help join evidence; they must not establish execution truth, task pass/fail, repository convergence, or product acceptance. MCP durable process/runtime receipts are the authority for commands/tools/process identity, observed execution result, and tool ordering. GitHub commit/ref/PR/check/CI/immutable-artifact state is the authority for repository convergence and automated acceptance; GitHub issue prose remains intent/coordination evidence rather than runtime truth. Do not publish a replacement aggregate sanity score until those authoritative MCP + GitHub components have measured coverage and calibrated semantics.
   **Last-resort Library Inbox durability.** The fallback trigger is failure of the required normal durable/reporting toolchain, not MCP loss specifically. Use the normal canonical route whenever it is usable. When a substantive manual/supervising or timed worker run cannot complete a required durable worker report or canonical handoff because the needed normal route is unavailable or unusable — for example GitHub, MCPv4, MCPVisual, Remote Desktop Commander, user-manual PowerShell, or the canonical machine report helper — and ChatGPT Library remains available, write exactly one temporary markdown report to Library `/Inbox` with `handoff_state: TOOLCHAIN_RECOVERY_PENDING`, the intended canonical destination(s), and the concrete evidence already obtained. `/Inbox` is recovery state, not the final archive. This rule never authorizes scheduler mutation, prompt patching, or repurposing another scheduled worker as a courier. On the first later supervising/manual recovery session where the required normal routes are usable, inspect `/Inbox`, reconcile each entry into the applicable canonical worker-report/history, GitHub/repo/operator handoff and provenance destinations, verify durable landing, then delete only reconciled entries; a fully reconciled healthy state has an empty `/Inbox`. If Library is unavailable too, report the durability failure truthfully and never claim persistence.


9. **Repair minimally.** Recurring workers report bounded fleet-watch evidence but never perform scheduler recovery. The supervising/manual ChatGPT session or explicit operator handoff may identify the exact suspect canonical slot from reports/start receipts and, only when current user direction and `worker_recovery_guard.py` both warrant it, perform one targeted idempotent `is_enabled=true` recovery for that existing slot while keeping the enabled recurring count at or below five in that target subscription partition. Never create verifier, spare, overlap, replacement, or temporary sixth recurring workers inside either canonical partition.
