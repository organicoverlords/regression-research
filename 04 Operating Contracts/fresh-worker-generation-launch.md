# Fresh Worker Generation Launch Contract

Use this contract whenever starting a new recurring worker generation or replacing workers that are stale, buggy, or missing required tools.

Do not make Atlas or Vault a generic worker startup gate. For ordinary repository work, orient from current user direction and live repo/runtime state, then read the target repo's current `AGENTS.md` immediately before the first mutation. For stack/infra work only, use `Stack Atlas -> smallest relevant live owner -> targeted Vault history only if needed`; Atlas is navigation, live sources are truth, and Vault/reports are history or projections.

## Hard capacity: five workers total

- **Five is a hard maximum for the recurring worker fleet.** Never have more than five enabled recurring repo workers, even temporarily during replacement, recovery, verification, or generation turnover.
- **Replacement is one-for-one at the cap.** When five workers are enabled, retire/disable a proven-bad slot before creating or enabling its replacement. A verifier, spare, overlap worker, or "temporary sixth" is not allowed.
- Preserve healthy workers and fill only missing or proven-bad slots until the active enabled fleet reaches five. "Arm five" means reconcile the fleet to **at most five total enabled workers**, not add five workers on top of an existing fleet.
- A full healthy fleet is five workers. Fewer than five is allowed while a slot is intentionally missing or being repaired; more than five is never allowed.

## Mode decision: status first; replace only proven-bad slots

- Perform **one bounded status read** of the intended five worker slots before scheduler mutation: enabled state, schedule, and latest available run/report evidence. Do not repeatedly re-read the scheduler during setup.
- Treat a slot as bad only when current run evidence plus independent execution evidence shows a persistent worker/session defect that prevents useful execution across supported routes. One or a few MCPv3/tool/binding/transport failures are not enough; route failure is local and recovery/fallback comes first. When a slot is genuinely bad, retire/remove only that slot and create a fresh replacement; start with Worker 1 when Worker 1 is the bad slot.
- Preserve healthy intended workers. Re-enable an otherwise healthy paused/disabled worker when needed; do not recreate healthy slots merely to make the fleet uniform.
- Replace the **whole generation** only when the user explicitly requests all-fresh workers, describes the whole fleet as poisoned/contaminated, or current evidence shows a shared generation defect. One bad worker is not evidence that all five are bad.
- Historical reports, templates, schedules, and memory are evidence only. Current user direction and current run/report evidence control the decision.
- **Ownership is collision state, not worker status.** BusyCoordinator claims, leases, heartbeats, and checkpoints add zero positive liveness or progress evidence. Current status comes from a bounded recent MCP execution window tied to the worker/scope: in-flight execution or a continuing stream of recent completed work counts as active; do not require a child process to exist at the exact sampling instant. If neither is observed, answer not working. Claim timestamps may bound how much real work happened during the reservation, but only concrete work output counts. Reconcile collision-control state separately.
- Reconciling the five intended slots is one setup pass. Do not insert proof ceremonies between Workers 1-5; establish five enabled slots, then use Worker 1 execution proof as the first acceptance gate.
- **Visual proof is an artifact pointer, not a worker assertion.** When a worker produces player-visible proof, its current automation-ID keyed snapshot under `worker-reports/current/<automation-id>.md` (or its immutable archived report) must include `visual_proof_run`, `visual_proof_claim`, `visual_proof_review`, and `visual_proof_reviewed_json`. `visual_proof_review` starts as `PENDING_REVIEW`; the worker may not promote its own capture to `PROVEN`.
- **Visual review never blocks the worker fleet.** After publishing the raw proof and report pointer, the worker continues useful work. An independent reviewer inspects the actual local proof run under `C:\P3Proofs` (video/frame sequence/contact sheet) and writes `reviewed.json`; only that file may change the reportable claim state to `PROVEN`, `REJECTED`, or `NOT_PROVEN`. Missing/bad proof blocks only that visual claim, not unrelated execution.
- **Keep current state and history separately, with automatic metrics.** Worker names are mutable display labels only. They are never identity, discovery keys, scheduler-slot keys, supervision-event keys, or liveness keys. The stable current-snapshot key is the scheduler automation/task ID: `worker-reports/current/<automation-id>.md`. When a worker is created, inject its automation ID into its prompt/report contract; renaming the task must not move or fork that snapshot. A replacement automation gets a new ID and therefore a new snapshot. Every substantive finalized run must be archived immediately with `python C:\Users\Lauri\Desktop\vault\tools\worker_report_history.py archive --report <path>`; canonical immutable run identity is the report SHA-256 under `worker-reports/history/_reports/`. Supervisors discover recent work from `metrics.json.latest_reports` or immutable report hashes ordered by time, never by remembered names and never by `by_worker` grouping. `display_label` is optional presentation metadata; `automation_id` identifies the current scheduled slot; neither replaces the report hash as run identity. Keep each report compact and factual (`automation_id`, optional `display_label`, `started_at`, `last_activity_at`, repo/scope, state/outcome, mutation/PR/merge, validation, remaining gate, and proof pointers when applicable). Every finalized run adds `stop_reason`: `TIME_WINDOW`, `SCOPE_COMPLETE`, `WAITING_EXTERNAL`, `TOOL_BLOCKED`, `RESOURCE_BLOCKED`, `NO_SAFE_WORK`, `INTERRUPTED`, or `OTHER`; add `stop_detail` only when needed. Classify tool-surface failures as `transport_drops`, `binding_drops`, `safety_blocks`, or `other_tool_failures`; ordinary command/test exit codes are not tool failures. When any class is nonzero, add `tool_failure_effect: RECOVERED_CONTINUED|CONTRIBUTED_TO_STOP|BLOCKED_REQUIRED_ROUTE`. A transient failure does not justify stopping while supported fallback or safe useful work remains. Archiving refreshes `metrics.json`; workers must not manually maintain aggregate metrics.
- **Keep the commit-identity gate small.** Immediately before a commit run `python C:\Users\Lauri\Desktop\vault\tools\git_identity_guard.py --repo "<repo_path>"`; if it rejects unusable identity, rerun that same command with `--fix-from-gh`, then audit once more. Do not fetch Vault, pipe `git show` into Python, or bundle unrelated git/gh discovery into the commit gate. The supervisor keeps the local guard file synchronized with the merged Vault source.
- **Current user-directed product outcome outranks owned-delivery cleanup.** At each run start, briefly inspect the worker's own open PRs/branches, but do not let old PR/check/merge hygiene monopolize the run. Finish prior owned work first only when it directly blocks the current user-directed product outcome or can be closed immediately with a bounded action. Otherwise preserve its exact gate and move to a safe non-conflicting scope that advances the current player-visible product goal. Publishing a PR, pushing a commit, or passing local tests is progress, not completion, but waiting on hosted checks is not a reason to spend the rest of the run on convergence. Recurring runs have about 24 minutes of useful execution budget: spend it on substantive implementation, runtime acceptance, or other direct product movement. Do not idle or pad merely to hit a duration; duration is diagnostic data, never completion proof.
- **Report delivery state, not timer state.** Use `RUNNING`, `WAITING`, `BLOCKED`, or `COMPLETE`; do not write `DONE`. `COMPLETE` requires the bounded outcome landed or closed, required gates resolved, the exact claim released/completed, and task-created branch/worktree cleanup finished. A run ending with an open PR, check, merge, proof, or cleanup gate is `WAITING` or `BLOCKED` with `remaining_gate` and the exact next action.

1. **Check once, replace minimally.** Read current worker status once. Retire/recreate only slots with current evidence of poisoning, stale/broken execution, or required-tool failure; preserve healthy slots and their schedules where practical. Do not inherit a failed worker's conversation state as launch authority.
2. **Arm the intended five in one setup pass and schedule Worker 1 once with enough runway.** Use about **5 minutes** as the normal Worker 1 target. If setup latency makes that too short, choose a later safe launch time **once** before the setup report. The launch window is a scheduling parameter, not a precision invariant: a longer runway is preferable to repeatedly moving Worker 1 forward. Workers 2-5 may remain on healthy existing schedules or be staggered behind Worker 1 as needed; all five intended slots must be enabled before setup is reported complete.
3. **Verify once, then lock the scheduler phase.** After the necessary mutations, perform one bounded readback confirming the intended five enabled slots and that Worker 1 has a future launch with reasonable runway. If the committed Worker 1 time is already invalid (past/current minute or too close to finish setup safely), move it forward **once** before reporting. Do not move Worker 1 merely because time elapsed while inspecting or reporting. Give one compact setup report and end the arm phase.
4. **Go work; do not idle or re-arm.** Immediately return to substantive repository work in the same chat. From the setup report until the first post-launch check, do not rearm, reschedule, replace, pause, disable, or otherwise mutate worker scheduling. Waiting, rapid polling, scheduler normalization, repeated verification, or keeping the turn alive only to watch a timer is not productive supervision.
5. **Use the current production route order and keep failures local.** MCPv3 via the VPS is primary. If it actually fails or is unavailable, continue through `plugin2`; Remote Desktop Commander and the hosted GitHub connector are not fallbacks. MCP0 is retired. Do not require a prompt tag for a specific connector, do not turn route recovery into the mission, and do not use OAuth/authentication repair as troubleshooting. Preserve returned process IDs and task state across recovery. Refresh/re-discovery/reload is **repeatable, explicitly allowed, and may be mandatory many times** when bindings disappear or go stale; there is no one-refresh ceiling or fixed failure-count cutoff. Never tight-loop. A route may be reported unavailable only from current repeated evidence after appropriate recovery, and even then the worker continues safe useful work through another supported route or independent work when possible. For MCPv3 `start_process`, write Windows PowerShell 5.1-compatible commands: no `&&`, `||`, `??`, ternary syntax, `$PID` assignment, or direct `foreach {...} |` pipelines.
6. **Generic mission, product-first live queue.** Workers orient from current repo authority and live standalone BusyCoordinator state, then prioritize the current user-directed player-visible product outcome. Prefer gameplay/content/runtime-visible implementation and acceptance over infrastructure, policy, scheduler, coordination, documentation, PR hygiene, or hosted-check shepherding. Work infra/control-plane only when it is the actual blocker to that product outcome. Use current PRs/issues as delivery context, not as an automatic priority queue. When no explicit product direction is embedded in the worker prompt, read the project North Star before selecting new work, choose a concrete unmet player-visible outcome, avoid duplicates, and start advancing it in the same run.
7. **A scheduled/enabled worker is NOT a proven worker.** Fresh-generation acceptance requires observed live proof from Worker 1's first launch: the timer actually fired; MCPv3 was attempted as the primary machine route and either succeeded or an evidenced failure led to a supported fallback; a machine process route actually executed; local repo/GitHub checks succeeded where required; repo/head/remote identity was captured; current collision ownership was checked when mutation required it; and the worker selected and began a real bounded work scope. A task card, coordinator claim/lease/heartbeat/checkpoint, enabled flag, timestamp, report, or `last_run_time` alone is insufficient.
8. **Use an explicit first-launch proof surface.** Worker 1 may write a local non-Git proof record only after the required tool plus local `git`/`gh` succeed, ownership is checked, and substantive work begins. Never write the proof optimistically before those facts are true.
9. **Verify Worker 1 while doing real work, not by idling.** Continue substantive repo work until Worker 1's launch window has elapsed, then check the automation run and proof surface at a natural work boundary. If Worker 1 is healthy, continue the supervising chat's repo work until the current bounded task is done or a genuine task-level blocker is reached.
10. **A failed first launch replaces only the failed slot.** Do not call Worker 1 failed before its committed `DTSTART` plus normal scheduler latency has elapsed. If it then does not fire, cannot use the required tool, reports an evidence-backed tool/startup failure, fails live orientation, or lacks substantive launch proof, retire/recreate **Worker 1 only**, schedule the replacement once with enough runway (normally about 5 minutes; longer if setup requires it), perform one bounded readback, report the repair compactly, return to substantive repo work, and check again after launch. Preserve Workers 2-5 unless their own current run/report evidence proves they are bad or there is evidence of a shared generation defect.
11. **The current chat is the supervisor; do not create a verifier timer as a substitute.** With all five worker slots armed, the supervising chat owns launch acceptance. A separate wakeup/verifier automation consumes capacity and recreates the same offloading failure. The supervisor reports setup, works productively, verifies Worker 1, repairs if needed, and keeps working.
12. **Keep user-visible supervision bounded and informative.** Report material setup, repair, and acceptance transitions. During longer repo work, give concise progress only after meaningful work or a direction change. Never use silence plus a continuously running tool timer as the supervision mechanism.
13. **Worker execution may never administer the scheduler.** A scheduled worker must not call automation-management tools, disable/pause/rename/reschedule itself, or mutate siblings. Tool loss is local to that route, not a scheduler event. A worker that previously proved the local route in an earlier run is not replaced merely because a later run has one or two route failures. Even after the bounded recovery sequence is exhausted, continue other safe useful non-mutating work when possible and leave the recurring schedule enabled. Fleet repair belongs exclusively to the supervising chat.

This launch contract is an orchestration invariant. **Five enabled recurring workers is the hard fleet cap. Check status once, preserve healthy slots, replace only proven-bad slots one-for-one, reconcile to no more than five enabled workers, schedule Worker 1 once with enough runway, report setup, go work, then perform one post-launch acceptance check.** Never create a sixth worker as a verifier, spare, overlap, or temporary replacement. Do not trade fleet liveness for scheduler precision, and do not re-enter the arm phase merely because time elapsed. Schedule configuration is setup; observed execution proof is acceptance.
