# Fresh Worker Generation Launch Contract

Use this contract whenever starting a new recurring worker generation or replacing workers that are stale, buggy, or missing required tools.

1. **Replace poisoned workers; do not merely re-arm them.** Retire stale/buggy/missing-tool workers and create a fresh generation. Do not inherit their conversation state as launch authority.
2. **Default generation size is four workers.** Create four generic orchestrator/execution workers. Worker 1 launches as soon as practical; Workers 2-4 are staggered behind it so the first launch can be proven before the rest of the generation reaches full concurrency.
3. **Bind the required local tool route explicitly.** Put the required tool tag at the start of the worker prompt (currently `@plugin2`). GitHub work goes through the user's local machine using local `git`/`gh` via that process route. Do not request, authenticate, repair, or fall back to a hosted/OpenAI GitHub connector.
4. **Generic mission, live queue.** Workers orient from current repo authority and live coordinator state, then work current PRs/issues. They are executors/orchestrators, not status monitors. If the live issue/PR queue is genuinely exhausted, read the project North Star, identify a concrete unmet outcome, avoid duplicates, populate one bounded real tracker item when warranted, and start advancing it. Never terminate merely because nothing is assigned.
5. **A scheduled/enabled worker is NOT a proven worker.** Fresh-generation acceptance requires observed live proof after Worker 1's first launch: the timer actually fired; the required local process tool actually executed; local repo and local GitHub CLI checks succeeded; repo/head/remote identity was captured; and the worker selected/began a real bounded work scope. A timestamp alone is insufficient.
6. **Use an explicit first-launch proof surface.** Worker 1 may write a local non-Git proof record only after the required tool plus local `git`/`gh` succeed. Never write the proof optimistically before those calls return successfully.
7. **Do not idle while waiting for Worker 1.** If the supervising ChatGPT run is still active, keep doing useful project work during the launch window, then verify Worker 1 before ending the run. If the supervising run cannot remain active, create a one-shot self-wakeup shortly after Worker 1's expected launch; on wake, verify Worker 1 before treating the generation as healthy.
8. **Failed first launch means the generation is not accepted.** If Worker 1 reports missing tools, fails the required route, glitches before live orientation, or lacks concrete proof, retire/recreate the bad worker and diagnose the exact launch path. Do not simply hope the next hourly recurrence fixes it. Keep later workers from becoming the substitute proof for a broken first launch.
9. **After proof, continue normal orchestration.** Once Worker 1 is proven healthy, continue useful hands-on work as appropriate, then end the supervising run. Recurring workers remain enabled until the user explicitly stops them or the recurring mission is truly complete.

This launch contract is an orchestration invariant. Schedule configuration is setup; observed execution proof is acceptance.
