# Recurring Worker Contract

This file owns only the scheduler/worker boundary. Cross-project safety, routing, repository, evidence, and coordination rules belong to the shared policy or the narrow live owner that actually enforces them.

## Invariants

1. **Five is a hard maximum for the recurring worker fleet.** Never enable more than five recurring repo workers.
2. **The scheduler provides recurrence only.** Enabled state, schedules, timestamps, claims, leases, heartbeats, and reports do not prove that work is happening.
3. **Workers never administer workers.** A scheduled worker must not pause, disable, enable, reschedule, rename, replace, create, or delete itself or a sibling. Fleet administration belongs to the supervising chat.
4. **Use current direction and live state.** A worker follows its current run prompt and the live target repo/runtime. Read the applicable repo `AGENTS.md` immediately before the first mutation. Do not make Atlas, Vault, reports, history, or scheduler metadata a generic startup gate.
5. **Do product work for the useful run window.** Prefer concrete player-visible implementation and acceptance. About 24 minutes is a utilization target, not a reason to idle or pad. Finishing one bounded slice early should lead to another safe useful slice while meaningful time remains.
6. **A blocker changes scope; it does not end unrelated work.** Pending CI, an occupied Unreal/build lane, resource pressure, a route failure, or another actor owning an exact mutation scope blocks only that dependency. Preserve its gate and continue safe non-conflicting work when available.
7. **BusyCoordinator is collision control only.** Claim only the exact shared mutation scope when collision risk exists. It is not backlog, scheduling, liveness, priority, capacity, or worker supervision.
8. **Keep reporting small, with automatic metrics.** Immediately before writing or finalizing a worker report, after a machine route is established, read this contract once; do not rely on copied or remembered reporting instructions. A missing machine route must not make an unattended worker ask the user for action, pause itself, or stop useful work; use the canonical schema already present in the current automation prompt until the route is available. Write `worker-reports/current/<automation-id>.md` with these exact canonical keys: `automation_id`, optional `display_label`, `started_at`, `last_activity_at`, `repo`, `scope`, `state`, `outcome`, `mutation`, `validation`, and `remaining_gate`; add landed/published proof fields when applicable. Do not substitute aliases such as `mutations` or `remaining_heavy_gate`. Near the start of every timed run, after the first bounded scope selection and before any command that may consume a material part of the useful run window, create or refresh that current report with `state: RUNNING` and the run's actual `started_at`; update it at natural checkpoints when the scope or evidence materially changes. This early current report is not archived and does not prove liveness; it exists so an interrupted run cannot leave the prior run presented as current. Every substantive finalized run must be archived immediately with `python C:\Users\Lauri\Desktop\vault\tools\worker_report_history.py archive --report <path>`; the archiver rejects malformed current reports, derives duration/utilization, and refreshes `worker-reports/metrics.json`. If the archiver rejects a premature `RUN_FINISHED`, the run is not finished: keep the current report in `RUNNING`, continue useful P3 work, and do not end/final-answer the worker turn until finalization is accepted or the user interrupts/supersedes the run. Do not satisfy the guard by merely rewriting `stop_reason`. A report is evidence of that run, not proof of present liveness.
9. **Repair minimally.** The supervisor replaces only a currently proven-bad slot and never exceeds the five-worker cap. Do not create verifier, spare, overlap, or temporary sixth workers.
