# Recurring Worker Contract

This file owns only the scheduler/worker boundary. Cross-project safety, routing, repository, evidence, and coordination rules belong to the shared policy or the narrow live owner that actually enforces them.

## Invariants

1. **Exactly five canonical recurring workers stay enabled.** Five is both the requested fleet size and the hard maximum. Never pause, disable, delete, retire, reschedule, rename, or replace a canonical worker unless the user explicitly instructs that exact scheduler mutation. An unexpected disabled canonical worker is degradation to repair, not a safe steady state.
2. **The scheduler provides recurrence only.** Enabled state, schedules, timestamps, claims, leases, heartbeats, and reports do not prove that work is happening.
3. **Every recurring worker is also a bounded peer-recovery orchestrator.** A worker must never administer itself and must never pause, disable, reschedule, rename, replace, create, or delete any worker. After its own fresh timed report exists and `worker_report_history.py begin` succeeds, each worker performs one bounded fleet-health check per run; never poll or loop on scheduler state. If any canonical sibling is disabled and there is no explicit user instruction preserving that disabled state, re-enable that sibling once with `is_enabled=true` only; preserve its prompt, title, schedule, timezone, and stagger. Do not require a particular failure signature before restoring the requested 5/5 enabled fleet. Scheduler/report timing remains evidence for diagnosing why the sibling disabled, not an admission gate for restoration. Never touch retired, test, legacy, or non-fleet automations. Every peer-recovery check and action must be recorded in the acting worker's own durable report before product-repo mutation continues. Each run must put one explicit `Peer recovery:` entry in `findings`: either `none needed`, `scheduler control unavailable: <reason>`, or the action taken. For an action include the sibling label/id, scheduler last_run_time, disable/update time when available, exact `is_enabled=true` action, and result. If scheduler state/control is unavailable, tag the finding `route_problem`, record it, and continue product work; never silently omit the check. This narrow peer-recovery authority is part of normal worker orchestration and does not create a sixth supervisor slot.
4. **Use current direction and live state.** A worker follows its current run prompt and the live target repo/runtime. Read the applicable repo `AGENTS.md` immediately before the first mutation. Do not make Atlas, Vault, reports, history, or scheduler metadata a generic startup gate.
5. **Do product work for the useful run window.** Prefer concrete player-visible implementation and acceptance. About 24 minutes remains the timed utilization target and is not a reason to idle or pad. Finishing one bounded slice early should lead to another safe useful action while meaningful time remains. Utilization never requires creating a new work identity; work identity follows the canonical shared issue-first rules, so continue existing WIP/current acceptance identity instead of inventing filler. Timed finalization keeps the existing >=80% completion guard, with only user interruption/supersession or the documented true no-safe-work exception allowed to finish earlier.
6. **A blocker changes scope; it does not end unrelated work.** Pending CI, an occupied Unreal/build lane, resource pressure, a route failure, or another actor owning an exact mutation scope blocks only that dependency. Preserve its gate and continue safe non-conflicting work when available. **If a required tool or binding is missing, unavailable, stale, disconnected, or unexpectedly rejected, refresh/re-discover the available tool bindings and retry through the supported route before using a supported fallback. Treat missing tool exposure as route state, not proof that the capability is absent. A tool/route failure by itself is never authority to pause, disable, reschedule, or otherwise administer this worker or any sibling; the only exception is the bounded sibling re-enable in invariant 3 after the full independent scheduler/report signature is proven.**
7. **BusyCoordinator is collision control only.** Claim only the exact shared mutation scope when collision risk exists. It is not backlog, scheduling, liveness, priority, capacity, or worker supervision.
8. **Keep reporting durable and population-separated.** Immediately before writing or finalizing a worker report, after a machine route is established, read this contract once; do not rely on copied or remembered reporting instructions. Reporting is evidence/observability only and never completion, scheduling, supervision, admission, or a queue. Both timed and manual/on-demand workers record the same structured finding fields: `finding_tags` and `findings`. Canonical tags are `bug`, `error`, `regression`, `wrapper_anomaly`, `route_problem`, `contention`, `performance`, `improvement`, `tooling`, `ci`, `build`, `proof`, `resource`, and `other`; use `finding_tags: none` and `findings: none` when nothing material was observed.

   **Timed recurring runs** keep the existing `worker-reports/current/<automation-id>.md` -> `worker-reports/history` lifecycle and `worker-reports/metrics.json`. Use the canonical keys `automation_id`, optional `display_label`, `started_at`, `last_activity_at`, `repo`, `scope`, `state`, `outcome`, `mutation`, `validation`, `remaining_gate`, `finding_tags`, and `findings`; when a run publishes a durable proof/capture bundle, use optional `proof_artifact` for its canonical review/index/receipt path and `proof_artifact_sha256` for that exact file digest. Historical `proof_index` / `proof_index_sha256` remain accepted aliases. These fields are navigation/integrity evidence only and never imply visual review or PASS. Near the start of every timed run, after the first bounded scope selection and before any command that may consume a material part of the useful run window, create or refresh that current report with `state: RUNNING` and `started_at` set to the current machine time, then immediately register the start with `python C:\Users\Lauri\Desktop\vault\tools\worker_report_history.py begin --report <path>`. The begin command writes the machine-observed start receipt used for timed duration/utilization; self-reported backdating does not count. Update the current report at natural checkpoints when scope/evidence/findings materially change. Finalize and archive it with `python C:\Users\Lauri\Desktop\vault\tools\worker_report_history.py archive --report <path>`. A current timed `RUN_FINISHED` without matching machine start evidence is rejected; successful archive consumes the receipt. If the archiver rejects premature timed `RUN_FINISHED`, the run is not finished: keep the current report `RUNNING`, continue useful work inside existing WIP/current work identity, and retry finalization only when valid. Duration and target utilization remain derived observability metadata, while the timed finalization guard enforces >=80% utilization except user interruption/supersession or the documented true no-safe-work condition. The guard is not scheduling, priority, product acceptance, or permission to manufacture filler issues/PRs.

   **Manual/on-demand runs are mandatory and minimal.** Each substantive user-driven execution turn gets a fresh filesystem-safe `run_id` and one `worker-reports/manual/current/<run-id>.md`. The required fields are only `run_id`, `started_at`, `last_activity_at`, `repo`, `state`, and a short `outcome`; `display_label`, `scope`, `finding_tags`, `findings`, and proof-artifact fields are optional. Open the report once immediately before the first tool call and close/archive it once immediately after the last tool call before returning control to the user. Do not checkpoint routine progress and do not copy commands, process IDs, Busy claims, GitHub/PR chronology, CI output, validation logs, or other telemetry already preserved by their owning systems. Use optional `findings` only for a material error, blocker, workflow defect, or reusable blindspot worth aggregating. Manual history derives start/finish/duration and aggregate finding statistics, never timed utilization/fleet statistics. A manual report is accounting/feedback evidence, not liveness, supervision, admission, or a queue.

9. **Repair minimally.** The supervisor replaces only a currently proven-bad slot and never exceeds the five-worker cap. Do not create verifier, spare, overlap, or temporary sixth workers.
