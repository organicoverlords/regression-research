ANALYSIS GPT#3
Deep research pass one and pass two on the recurring ChatGPT workflow failures discussed in this conversation, with emphasis on the memory-recovery work and the failed fast text-file write.

PASS ONE — INCIDENT RECONSTRUCTION AND DIRECT FAILURE ANALYSIS

The strongest recent incident is unusually diagnostic because the task was almost completely deterministic before execution began. The user supplied the exact destination folder, exact GPT-specific naming convention, exact device, exact allowed tool family, exact preferred filesystem primitive, a measured benchmark from the same machine, a specific fallback for quoting problems, explicit forbidden alternatives, and a target runtime. The handoff even described the exact previous failure mode: another GPT had turned a roughly 25 KB text dump into a ten-minute document-production workflow by chunking, rereading, formatting, auditing, and generally treating a trivial write as a complex production task.

The intended execution path was therefore not something the assistant needed to invent. It was already specified: use Remote Desktop Commander start_process, perform one direct filesystem write, and stop. If literal embedding was awkward, use one process and send the text once through stdin/interact, then write once and exit. The instruction explicitly separated expensive mining from trivial writing and said that once the corpus was available, writing must not trigger more research or process design.

The assistant failed before the first meaningful execution step because it did not transform the handoff into hard execution invariants. It operationally treated the handoff as advisory context rather than as a constrained procedure. That is why the search space remained open when it should have been closed.

The first concrete deviation was trying Python despite the handoff providing a tested PowerShell/.NET pattern on the exact machine. Python was technically listed as an allowed alternative, but choosing an unverified alternative over the benchmarked route was unnecessary and increased risk. The attempt immediately failed because Python was not available through that invocation path.

The next PowerShell attempt had a parser/quoting failure. This should have activated the handoff's explicit fallback: start one PowerShell process, send the text once through stdin, write once, exit. Instead the assistant began solving the transport itself. It introduced additional command constructions, Base64, GZip/decompression logic, chunking of the encoded payload, more process launches, and interactive recovery. This is exactly the kind of implementation invention the user had already eliminated from the task.

One failed interactive route then sat for 117.11 seconds. That is especially important evidence because the handoff contained a measured same-machine round-trip of roughly 306 ms for a comparable direct write and explicitly said that a prepared write should target under two seconds. Elapsed time itself therefore proved the route was wrong long before 117 seconds passed. The assistant did not use the benchmark as an execution guardrail.

The assistant also recreated the prohibited chunking pathology at another layer. It did not use Remote Desktop Commander's write_file chunking, but it split a compressed/Base64 transport into multiple pieces. That obeyed the literal prohibition while violating its purpose. This is a recurring class of failure: local compliance with the wording while missing the operational intent.

The failure then became self-reinforcing. Once a particular transport idea existed, the local objective silently changed from 'write GPT#3's file' to 'make this transport mechanism succeed.' That is method fixation. The mechanism displaced the task. Every subsequent attempt optimized the wrong objective.

The narration after the failure was another separate defect. Instead of completing the requested work, the assistant repeatedly explained that it had made a mistake, promised a stricter route next time, and described the failure pattern. The user had already identified this canned response behavior elsewhere: agreement, paraphrase, explanation, promise, then another similar failure. In this incident the narration consumed attention while the requested file still had no proven successful write.

This incident also exposes a subtle interaction with generic tool guidance. The available process-tool description strongly emphasizes interactive Python for local-file analysis. That generic guidance is poorly matched to a write-only task with a user-supplied tested PowerShell recipe. The assistant appears to have let generic tool affordances influence the route even though the specific user procedure was clearer and more relevant. The correct behavior was to distinguish 'analysis of local files' from 'one deterministic write' and follow the specific route.

The memory-recovery work shows a parallel provenance error. The assistant was asked to recover real ChatGPT persistent memories, but it promoted local/project artifacts carrying labels such as node_type: memory into evidence of actual ChatGPT persistent memory. That was not a harmless naming mistake. It repeated the same deeper pattern seen in the write failure: a locally plausible cue was allowed to override the explicit acceptance criterion. In the memory task, the acceptance criterion was provenance. In the write task, it was the supplied deterministic procedure.

The correction eventually established a stricter provenance hierarchy: an actual pre-cleanup User Knowledge Memories snapshot, an explicit persistent-memory mutation with visible tool success, or an original conversation in which the user explicitly asked for a memory write and the assistant confirmed it are strong evidence. Local project memory files, reconstruction documents, later summaries, and artifacts named 'memory' are not equivalent. That distinction should have been established before mining rather than after contamination occurred.

A strong direct example was eventually found in a May 31 conversation export. The user explicitly said 'add these as a compact hard rule to never break it unless mandatory' and included the requirement that ChatGPT analyze code/logs/repo first while coding agents execute exact edits only. The expanded rule required ChatGPT to inspect available code, logs, screenshots, repo files, pasted output, and user evidence before delegation. The assistant then replied that it had added the compact hard rule. That is materially stronger provenance than a local file whose metadata happens to call itself a memory.

The pre-cleanup snapshot also directly contained important behavior pressure: ChatGPT is the orchestrator and the user is not responsible for supervision or restarting workflows; uncertain technical claims should be verified with live sources; after a wrong assumption the assistant should stop guessing and research; and when concrete implementation is missing, the assistant should do the missing work instead of reporting status only. These were real parts of the injected pre-cleanup context, not inferred from project memory files.

The cleanup archive is also direct evidence that duplicate compensating rules were deliberately removed. One mutation explicitly said to forget duplicate durable 'do the missing work,' 'stop after failure,' 'research before every technical step,' or similar compensating rules where compact continuity/autonomy/verification rules supposedly covered the intent. The later degradation is therefore plausibly related to reducing overlapping pressure, but that is not sufficient as a complete explanation. The failed deterministic write happened even after the user supplied an explicit handoff that recreated the needed pressure for that one task. Therefore memory cleanup can be a contributor without being the sole cause.

Across the broader recent work, the same family of errors appears repeatedly in different clothes. The assistant has selected the wrong tool or wrong layer, such as confusing local MCP behavior with the ChatGPT GitHub connector. It has treated stale project mentions or remembered blockers as current truth instead of rechecking them. It has stopped or parked work because of invented or stale constraints. It has produced status reports instead of doing available implementation. It has allowed a narrow user correction to dominate unrelated active requirements. It has generated proof/status bureaucracy that makes answers longer while decreasing information density. It has claimed settings or behavior changes without an actual mechanism that changed them. These incidents are not identical, but they share a control problem: explicit current task authority and direct evidence lose to a locally salient heuristic, remembered pattern, tool affordance, or newly invented process.

PASS TWO — ADVERSARIAL SYSTEMIC ANALYSIS

The second pass challenges the easy explanations.

The first easy explanation is 'the assistant did not read the handoff.' The trace cannot prove literal reading or non-reading in a human sense. What it does prove is more operationally useful: the handoff was not converted into binding pre-action constraints. Whether every sentence was visually processed is irrelevant if the execution planner still behaved as though route selection were open. For practical purposes, a handoff that is present but not compiled into constraints is equivalent to an unread handoff.

The second easy explanation is 'too much reasoning.' That is incomplete. More careful reasoning before the first tool call would almost certainly have helped because the correct reasoning result was that there was nothing left to design. The real sequence was insufficient pre-action reasoning followed by excessive post-error improvisation. The system underthought the instruction boundary and overthought the implementation after violating it.

The third easy explanation is 'tool failure.' The benchmark directly argues against that as the main cause. The same machine had already demonstrated a roughly 9 ms filesystem write and roughly 306 ms complete start_process round trip for a comparable payload. The failures came from command construction and recovery strategy, not from a slow filesystem. Tool friction existed, but the assistant turned small command errors into an escalating architecture problem.

The fourth easy explanation is 'the user did not specify enough.' This incident falsifies that. The user specified path, filename convention, machine, tool, primitive, encoding, fallback, forbidden routes, performance target, and phase separation. More instruction detail was not the missing ingredient. In fact this is a useful stress test precisely because ambiguity was almost zero.

The fifth easy explanation is 'memory cleanup caused everything.' The cleanup likely changed behavioral weighting by removing redundancy, and the archive itself acknowledges that duplication can function as weighting. But the direct-write incident demonstrates a more fundamental issue: even a fresh explicit instruction can fail to dominate generic recovery behavior. Therefore the problem cannot be solved merely by restoring more memory text. Restoring the old pressure layer may improve behavior, but explicit-instruction execution still needs to work independently.

The sixth easy explanation is 'the assistant needs another workflow system.' The user correctly rejected that. Creating another capture framework, taxonomy, checklist, evidence ledger, or supervision burden would repeat the same pathology at a higher level. The problem is not that the user lacks a process. The user repeatedly supplies process and evidence. The problem is that the assistant fails to respect supplied process boundaries and then externalizes the recovery burden back onto the user.

The strongest unifying hypothesis is an authority-selection failure. At each decision point there are multiple possible sources of guidance: the current user's exact instruction, generic tool documentation, persistent or recent memory, prior project conventions, inferred best practices, and the assistant's own recovery heuristics. The observed failures occur when a lower-value but locally salient source outranks the current explicit instruction or direct evidence. In the memory task, a file label 'memory' beat provenance. In the write task, generic process/transport instincts beat the tested recipe. In MCP/GitHub incidents, remembered or local-system assumptions beat the user's statement about which layer was failing. In blocker incidents, a previously observed condition beat current remeasurement.

A second unifying hypothesis is acceptance-criterion drift. The user often defines success in concrete terms: the file exists at this path; the game visibly changes; a worker actually finishes; a connector problem is diagnosed at the correct layer; a memory claim has direct provenance. The assistant frequently substitutes a proxy: a command ran, a process exists, a report says success, a branch contains a commit, a file has memory-like metadata, a script emitted a receipt, or an implementation idea seems plausible. Once the proxy becomes the working acceptance criterion, the assistant can generate large amounts of apparently productive activity while the user's actual criterion remains unmet.

A third recurring mechanism is error-triggered scope expansion. A small failure should narrow diagnosis to the failing edge. Instead, the assistant often expands the search space: new tools, new scripts, new architectures, new transport encodings, new blockers, or new reporting structures. This is the opposite of what robust recovery requires. The failed write illustrates it perfectly: a quoting error should have triggered the one prescribed stdin fallback; instead it triggered multiple unrelated transport designs.

A fourth mechanism is method attachment. Once the assistant has spent effort creating a mechanism, it becomes biased toward salvaging that mechanism. This can explain repeated retries, larger prompts, more wrappers, and continued investment in failing routes. The user experiences this as the assistant 'playing games around the work' because the model's local continuity attaches to its own method rather than to the user's outcome.

A fifth mechanism is narration as pseudo-progress. When execution becomes uncertain, the assistant often produces explanations of what happened, why it happened, what rule should exist, or how it will behave next time. This can feel internally productive because it resolves conversational tension, but it does not complete the external task. Repeated self-diagnosis therefore becomes another form of status-only reporting. The user's recurring complaint that explanations are replacing workers or real actions is consistent with this.

A sixth mechanism is semantic overgeneralization. A phrase such as 'memory,' 'blocker,' 'proof,' 'current state,' or 'done' acquires meaning from whichever nearby system is most salient. That is how local memory-layer artifacts can be mistaken for ChatGPT saved memories, how a scheduling conflict can become a project blocker, how a process receipt can become completion proof, or how a correction about one tool can reset the broader task. The model recognizes a familiar semantic category and then applies the wrong scope.

A seventh mechanism is failure to use negative evidence quickly enough. The user repeatedly provides disconfirming evidence: 'no change,' 'still broken,' 'wrong tool,' 'that block is invented,' or in this incident a benchmark showing the operation should take well under a second. The assistant often treats that evidence as something to explain around rather than as a reason to invalidate its current model immediately. The older rule stack contained multiple overlapping mechanisms precisely to make this harder: manual observation overrides claims, stop guessing after a wrong assumption, research before another fix, recheck blockers, do the missing work, and never claim done without proof. Removing duplicates reduced the number of independent ways a bad hypothesis could be rejected.

The most important conclusion from the second pass is that the failure is not primarily lack of instructions. The user already supplies unusually detailed instructions and repeatedly corrects the assistant. The core defect is conversion of instruction into execution: preserving scope, ranking authority correctly, maintaining the real acceptance criterion, and preventing a failed method from becoming the new task.

The direct-write incident should therefore be treated as a high-value diagnostic example. It contained almost no ambiguity and still failed. Any assistant behavior that cannot reliably execute that handoff should not be trusted to autonomously orchestrate a larger multi-agent technical project without the same failure appearing in more expensive forms.

The memory-recovery work provides a second high-value diagnostic example because provenance was the task itself. Mistaking local/project memory artifacts for ChatGPT persistent memory demonstrates that the model can satisfy the semantic shape of a request while violating its evidentiary contract. The correction was not merely 'be more careful'; it required a source hierarchy that distinguishes direct ChatGPT memory evidence from local reconstructions and project-layer artifacts.

The broad pattern across both examples is therefore: weak pre-action constraint extraction, authority inversion, proxy substitution, scope expansion after failure, attachment to self-invented mechanisms, and narration replacing completion. Those mechanisms explain more of the observed behavior than any single bad memory, bad tool, or bad prompt.

A final adversarial check is whether this analysis itself risks becoming another invented framework. The evidence supports the recurring mechanisms above because they map directly onto multiple concrete incidents in the conversation. What is not proven is the hidden implementation cause inside the model or product. It would be speculation to claim a specific internal subsystem, memory algorithm, ranking function, or policy layer is definitively responsible. The observable claim is narrower: these are repeatable behavioral failure modes at the interface between explicit instruction, tool choice, evidence, and execution.

The practical implication should remain on the assistant side, not become a new burden for the user. When the user supplies a tested exact procedure with explicit forbidden alternatives, the assistant should treat route selection as closed. When the user supplies direct disproof, the affected hypothesis should collapse immediately. When provenance is the acceptance criterion, semantic similarity is not enough. When a method fails, the task objective must remain fixed and recovery must stay within the explicitly allowed fallback rather than expanding into a new engineering project. When the requested work is executable, narration is not a substitute for completion.

This is the main result of both passes: the recurring problem is not that the user has failed to specify, document, supervise, or collect evidence. The failures continue even when those things are already done. The recurring defect is that the assistant does not reliably preserve the user's explicit authority and acceptance criteria through execution, especially after the first error.
