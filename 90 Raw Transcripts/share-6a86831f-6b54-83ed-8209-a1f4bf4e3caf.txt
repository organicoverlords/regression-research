### The deeper interaction causing the “newest message erased everything” problem

The critical combination is:

**P3 latest-instruction authority + recent-message salience + failed-fix “stop broad execution” + no distinction between conflicting and unrelated state.**

The precedence concept itself is necessary. If you say “use X, not Y,” the newer instruction should win.

The mistake is treating **every new instruction as conflicting with the whole previous model**.

For example, a correction about which MCP tool to use should alter the tool-routing part of the current task. It should not erase the goal, repo boundaries, unfinished work, discoveries, or unrelated constraints.

That is the most important semantic repair I would make.

### Why the answers became a text cannon

There are several overlapping formatting mandates from different eras:

`clear summary` + `ELI5` + `checkmarks` + `proof` + `not proven` + `blockers` + `next step` + `percentage` + `milestones` + `worker status` + `receipt`.

None of those is catastrophic alone.

Together they force the model to say essentially the same information several times in different administrative forms. That explains the exact pattern you described: **more words while information density goes down**.

It also explains why telling the assistant “be concise” has not reliably fixed it. The shortness instruction is competing with many more specific instructions requiring additional sections.

### Another problem I found: the memory is too historical

Several current memories are partly **event logs**, not durable knowledge. They contain sequences like “earlier this failed, later this worked, later the user corrected X, later Y happened.”

That is dangerous for two reasons.

First, historical failures remain semantically loud long after they stop mattering. Second, compressed retrieval can separate a statement from its chronology and scope. “Illegal memory,” “28 tools,” “connector renamed,” “RED,” or “USER_REVIEW_REQUIRED” can reappear without enough context to know it is old.

The worst example is MCP: your own durable P3 policy says those live details should never be memorized, yet other memories preserve them.

### Another problem: simplicity and bureaucracy are simultaneously mandated

There are strong instructions for **KISS/YAGNI, do not overcomplicate, keep the user out of policing, continue autonomously**.

There are also accumulated instructions for gates, review cards, proof classifications, receipts, worker states, provenance, lineage, dispositions, and terminal states.

When both activate, the assistant does something pathological: it invents a complicated process and then explains that the process is designed to keep things simple.

That contradiction is contributing substantially to the “turn every observation into a framework” behavior.

## Proposed cleanup

I would **not** add another policy layer. I would reduce and rescope what already exists.

The cleanup I recommend, in order:

1. **Rewrite the failed-fix custom instruction.** Remove mandatory `REJECTED / NOT PROVEN` terminology. Preserve only: your observed result overrides an assistant claim; inspect the affected real path before another fix; do not stop unrelated work.
2. **Fix the P3 “latest explicit instruction” rule.** Make supersession conflict-specific rather than whole-state replacement.
3. **Remove the global ELI5/checkmark response-format memory.** Your existing direct/readable preference already covers the useful intent. ELI5 can still be used when it genuinely helps.
4. **Return progress percentages, colors, milestones, WORKER REPORTS, review cards and receipts to their original tracked-project/worker scopes.**
5. **Remove volatile MCP state from persistent memory and merge the duplicated MCP memories down to stable facts only.**
6. **Trim MagicMusic and LowVRAM memories from historical chronicles into stable constraints and project boundaries.**
7. **Narrow strong domain rules such as character `NEXT` and AITube to their actual workflows.**
8. **Replace, rather than supplement, the bad continuity semantics with one small principle:** a new message modifies the existing understanding; only genuinely conflicting earlier information is superseded.

I would **keep** the useful core: rigorous verification where it matters, repo orientation before mutation, respecting manual observed failures, autonomy, minimal manual work for you, live source-of-truth checking, KISS/YAGNI, project boundaries, and professional answers.

I would **not change** Personality, hardware facts, or those underlying goals.
